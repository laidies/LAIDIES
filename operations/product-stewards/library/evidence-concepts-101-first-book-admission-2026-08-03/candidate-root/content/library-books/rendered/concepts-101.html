Everyone keeps saying "AI" like it's one thing you already know how to open. It isn't. Under that one name tag sits an engine, a pile of things it read once and then stopped reading, a working memory that fills up and starts dropping details, and a habit of sounding certain even when it's wrong. This book lifts the hood. No math — just the moving parts, what each one actually does, and where each one slips, so the next time someone says "just use AI" you know exactly what's down there.

Model / LLM

A model is the trained component of an AI system that turns an input into an output. It may produce words or images, interpret material, make a prediction or choose a next action.

Episode 05 uses one maintained picture for the relationship: the provider is the fashion house; the model is the house’s supermodel; an app is a boutique or department store where you may encounter one or more models. The picture helps separate the cast; the software is not literally organized like a fashion business.

An LLM—large language model—is designed to work with language. It may be one component in a larger system that also handles images, search, files, code or other tools. You do not need to memorize every model name. You do need to know that the model is not the whole product.

The four things people blur together

  • The provider develops and operates products and models.
  • The model transforms input into output.
  • The product supplies the interface, account, instructions, permissions, limits and visible features.
  • The tools let the system search, inspect files, run code or act through a connected service when the product permits it.

Some people use harness for the software that surrounds a model and helps it use tools or complete a workflow. It can be a useful engineering term, but it does not replace the four-part map above.

One product can offer several models, route between them automatically or hide the choice entirely. The same model can also behave differently when the product changes its instructions, context or available tools. A model is part of the experience—not the whole thing.

How models and modes differ

Models can differ in the material they accept, the outputs they produce, their speed, cost, context capacity, tool use and performance on particular tasks. Some products also offer modes that spend more computation before answering. Those modes can improve some multi-step work; they do not turn the result into verified truth.

Do not memorize a permanent “fast model versus reasoning model” rule. Product names, defaults and routing change, and not every provider exposes the same choice. “Reasoning” is also not a warranty: a slower answer can still begin from a bad assumption, misunderstand the task or use weak evidence.

Which one when

  1. What must the output be—text, image, analysis, code or an action?
  2. Does the task need current sources, files, calculations or another tool?
  3. What privacy, permission, plan or regional limits apply?
  4. How will you recognize a good result?
  5. Which important parts still require an outside check?

For a quick, recoverable task, the default option may be enough. For a complex task, a more capable model or deeper-computation mode may be worth testing. For a consequential task, the answer is never simply “use the expensive one”: use appropriate expertise, primary evidence and human review as well.

Where it goes wrong

Blaming the model for the whole result. The missing feature may belong to the product, plan, permissions, context or tools.

Treating a provider reputation as a task test. “Best writer” or “best reasoner” is too broad to decide whether this result serves this audience.

Equating more compute with correctness. Deeper processing can help without checking the source, jurisdiction, date or assumptions that matter.

Following a stale model guide. Names, defaults, prices and access change. Date every comparison and recheck it before teaching or buying.

A model is part of the experience—not the whole thing.

Provider, model, product and tools can each change what comes back. Name the layer before you try to fix it.

Try this

Choose one harmless task whose quality you can judge. In one product, note the date, visible model or mode (if the product shows it), tools and account plan. Run the task with the default option and one alternative available to you. Keep the request and context the same. Compare what each understood, what each made you fix and whether the extra time or cost improved this task enough to matter.

Training data

Training data is the collection of examples used to adjust a model while it is being built. The mix depends on the model and provider: it may include public, licensed, partner-provided, human-created or synthetic material, with filtering and later training stages used for different purposes.

  • Language models learn patterns from text and may also be trained on code, mathematics or structured examples.
  • Image, audio and video models learn patterns from the media types they are designed to accept or produce, often paired with labels or descriptions.
  • Multimodal models are built to work across more than one kind of material, such as text and images.

During training, the model’s parameters are adjusted as it learns patterns from those examples. That is different from the material available during today’s task. A document you attach, a page a search tool retrieves or a fact a product remembers can become current context without becoming new training data. The trained model is not automatically reading a live source when you ask a question; live information requires a product feature or tool that actually supplies it.

The cutoff, explained

A knowledge cutoff describes the boundary of the information represented in a particular trained model. It is not one date shared by every product, and the model’s own answer about its cutoff is not authoritative. Identify the exact model or product you are using, consult its current official documentation when a cutoff is published, and verify time-sensitive claims against current primary sources.

Imagine a friend who watched every episode of Sex and the City through the 2004 finale and stopped there. She remembers all of it — Carrie's column, the Aidan years, the Berger Post-It. Ask her about anything pre-2004 and she's flawless. Ask her about And Just Like That — about Big having a heart attack on the Peloton in the first episode of the spin-off — and she has nothing. That's not on her. That's where the watching stopped.

The model is similar: its trained knowledge is not a live feed. Three practical moves:

  1. Supply the current source. Paste the current policy, attach the recent document or provide the relevant passage. The model can use it as context, but you still need to check that the answer represents it correctly.
  2. Use a product with live retrieval. A search or retrieval tool can bring current material into the task. Check which sources it actually fetched and whether they support the answer.
  3. Check the exact product documentation. Model identity, cutoff, search access and source behaviour can differ by product, plan and date.

What you cannot do is treat a fluent answer as proof that a time-sensitive claim is current. Check the claim against a current official or primary source.

Where it goes wrong

The cutoff trap. You ask the tool about something current — last month's policy, this quarter's launch, today's news. The tool answers confidently, in the present tense, as if the information were live. It isn't. The model is filling in from old patterns. The most dangerous version: the tool invents a recent thing that doesn't exist (a product, a person, a paper) because the pattern of "a recent thing about X" is in its training data even when the specific X isn't.

How to spot it: anything time-sensitive. Anything with a version number or a date. Anything where "as of when?" is a fair question.

She graduated. She hasn't been to class since.

A trained model is not automatically following today’s news. For anything current, identify the exact model and product, then check the claim against a live official or primary source. A cutoff date can warn you about a boundary; it cannot certify that an older fact is still true.

Try this

Choose one time-sensitive answer from a tool you use. Record the exact product and visible model, if shown. Find the provider’s current official model information, then open the primary source for the claim itself. Compare what the product said with what each source actually establishes.

Token & context window

Two related ideas, often used interchangeably even though they're not the same.

A token is a chunk a model processes—often a word, part of a word or punctuation. Tokenization varies by model and language, so use the provider’s tokenizer or documentation when an exact count matters.

The context window is the bounded input a model can work with while producing a response. It may include instructions, conversation turns, retrieved passages or attached material, but the exact contents depend on how the product selects, truncates or summarizes them. It is working space for the current response, not the model’s training data.

Published context capacities vary by model and can change as products are updated. Check the current official page for the exact model and product you are using. A large advertised limit tells you what can fit; it does not guarantee that every detail will be used equally well.

Sounds enormous. It is. But there's a crucial second fact: more isn't always better.

The context window degrades under load

Longer input can make relevant information harder for a model to use reliably, even when the material fits within the advertised limit. The effect depends on the model, task, input structure and product.

In “Lost in the Middle: How Language Models Use Long Contexts”, Liu and colleagues tested selected language models on multi-document question answering and key-value retrieval. In those controlled tasks, performance often changed with the position of the relevant information and was frequently strongest near the beginning or end rather than the middle.

That study demonstrates a real position-sensitivity problem in the models and tasks it tested. It does not establish a universal percentage drop, prove that every current product behaves the same way or guarantee that the middle answer in your own document will be weakest. Practically:

  • Do not assume that fitting a document inside the limit means every passage will be used reliably.
  • Make the relevant evidence easy to locate and test whether the answer is supported by the source.
  • "Just paste in everything" is rarely as good as "paste in the relevant section, plus the one fact that matters."

Memory is not the context window

Quick clarification because the terms blur, and the difference matters.

Context window — the material available for this response

The product decides which instructions, turns, files and retrieved passages are placed on the desk.

Memory feature — product-managed context across conversations

A product may retain or synthesize selected details from earlier chats, files or settings and place relevant parts on the desk later.

Memory comes onto the desk as context. What can be retained, how it is selected, whether earlier chats or files can be referenced and which controls are available all depend on the product, account and settings. Do not assume that a new chat forgets everything or that a memory feature preserves a complete project record. Check the product’s current documentation and re-supply any source or constraint the task cannot safely proceed without.

How to use the window well

Three moves that compound.

  1. Keep one conversation focused on one thing. When you switch topics, start a fresh chat. Don't make the tool drag a 60-turn architecture discussion behind your follow-up question about formatting an email. The fresher the context, the sharper the answer.
  2. For long documents, make the evidence findable. Supply the source clearly, name the passages or questions that matter, and require the answer to point back to them. Position can affect performance, but source checking matters more than a universal top-versus-middle recipe.
  3. Watch for drift, and reset early. The signal: tone shifts. Your original constraints get dropped. The answer paraphrases your source instead of quoting it. That's the model losing the thread. Close the chat, open a new one, and re-paste only the parts that still matter.

Where it goes wrong

The wall-of-text trap. You paste a 60-page document and ask three questions. By question three, the answer sounds right but is paraphrasing the gist rather than quoting the source. You won't catch the slip unless you check against the document.

The eternal-thread trap. You assume a long-running product thread still exposes every earlier detail to the model. The product may truncate, summarize or select prior material, and important constraints can be missed. Long projects need a maintained source of truth, not faith in chat history.

If she's losing the plot, turn the page.

Picture a chalkboard at a long study session. Six hours in, the formula from the top corner is long gone. When the tone drifts or your original constraints stop showing up, that's the board filling. Start a fresh chat with just the constraints and continue.

Try this

Two short experiments.

First, test position rather than assuming it. Use a harmless document whose answers you can verify. Ask comparable questions about passages near the beginning, middle and end. Check every answer against the document and note whether position changed accuracy for this product, model and task. One trial is an observation, not a universal benchmark.

Second, test continuity. In a long planning conversation, ask the product to restate the original constraints, then compare the answer with your source record. If anything material is missing, re-supply the authoritative constraints or begin a focused thread. Do not infer a universal failure point from the number of exchanges.

Hallucination

A hallucination is false or unsupported content delivered as part of an AI-generated answer. It might be one invented citation, wrong date or made-up detail inside otherwise useful work—not only a completely fictional response. The system is not lying; lying requires intent.

A hallucination can be a fabricated source (a real-looking journal article that doesn't exist), an invented quote, a wrong date, a person who never worked at the company AI named them at, a legal precedent that was never filed, a price that doesn't match the live one. The category isn't "obvious errors." It's "errors that look exactly like correct answers."

The risk varies by model, task, context and evaluation. Do not use one benchmark as a universal “hallucination rate.” A current system can still place one unsupported claim inside an otherwise useful answer, so consequential claims need evidence rather than a confidence score.

Why hallucinations happen

Generative models are built to produce plausible output from patterns in their training and the context supplied now. Plausibility and factual support are not the same target. Rare facts, missing context, ambiguous questions and weak source material can all create room for an answer that sounds right without being right.

OpenAI’s 2025 research adds another part of the picture: many common evaluations reward a lucky guess more than an honest abstention. That can encourage confident guessing. It is an important mechanism, not a complete single-cause theory for every hallucination in every model or product.

The practical conclusion is deliberately less dramatic: current systems can reduce hallucinations, but none earns a blanket exemption from checking.

How to reduce hallucinations

There is no magic sentence that makes an answer true. Use a checking design:

  1. Supply the right material. Give the system the current policy, document, dataset or source it should use.
  2. Ask for traceable support. Connect each consequential claim to the exact passage, calculation or source—not merely citation-shaped text.
  3. Permit uncertainty. Ask it to mark missing evidence, ambiguity and unresolved conflicts rather than fill the gap. Treat that as one useful instruction, not a guarantee.
  4. Use the right tool. Current facts may need live search; arithmetic may need code or a calculator; private or high-stakes work may need an approved specialist system or no public AI tool at all.
  5. Check outside the answer. Open the source, reproduce the calculation or ask a qualified person. Asking the same model to praise its own work is not independent verification.

Do not ask a consumer chatbot to reveal private internal reasoning as your quality check. Ask for evidence, assumptions, a concise method you can inspect or a result you can reproduce.

How to spot one

The deeper skill is detection after the AI has answered. The pattern that catches hallucinations is the Elle Woods move: look for the detail that doesn't survive contact with reality.

Chutney Windham gave a calm, confident, repeated alibi — she was in the shower right after a fresh perm. Sounded true. Sounded true twice. Fell apart on one specific check: you don't wash a fresh perm without destroying it. The story collapsed on a single piece of domain knowledge.

AI hallucinations work the same way. The answer is fluent, internally consistent, and confident. It collapses on the one specific check:

  • Does this link actually open?
  • Does the quote actually appear on that page?
  • Was this person at the title the model gave them?
  • Does this number match the source it cited?
  • Was this legal case actually filed? In which court? When?

Where it goes wrong

Trusting fluency. The output sounds right. It uses the right vocabulary. It's structured the way a real answer would be structured. Plausibility isn't truth. The most expensive mistakes in the corporate AI era so far have all had this shape: someone read a fluent AI answer, didn't verify, sent it to a client or a court or a board.

Asking the model "are you sure?" Asking AI to verify itself produces another fluent answer with no actual verification underneath. The model is generating "the kind of thing someone confident would say" — which is sometimes the same kind of thing it said the first time. That's Chutney repeating her alibi, not Elle finding the contradiction.

Confusing reasoning models with reliability. Reasoning models and product modes may improve performance on some multi-step tasks, but that is not a guarantee of factual accuracy. They can still misunderstand the task, use a weak source or produce an unsupported claim. More deliberate is not infallible.

Plausibility isn't truth.

The whole danger of a hallucination is that it wears the same confident voice as a correct answer. You can't hear the difference. You can only check it — one link, one quote, one number, against the real source.

Try this

Take a recent AI answer you used or nearly used. Pick one claim that carries a fact, name, date or number. Open the original source and ask three questions: does it say this, does it apply here, and is it current enough for the decision? The lesson is not how fast you can verify it. The lesson is whether the answer survives contact with the evidence.

The four types everyone argues about

Generative, reasoning, agentic, AGI. These four words get thrown around meetings — sometimes all in the same sentence — as if they were rival products you have to pick between. They're best understood together, because the whole point is how they differ. Picture the kind of show this brand was raised on: a group of friends fighting supernatural forces, each with a different role in the fight.

1. Generative AI — makes

Plain meaning. Generative AI produces content from your request and the material you give it: a paragraph, image, slide, song, video or piece of code. “Generative” describes what it produces; it does not tell you whether the content is true or whether the wider system can take actions.

2. Reasoning models — think first

The Watcher in the library. Works the whole problem through, then says what to do. Slower, and better at math, logic, multi-step plans — anything that needs its work checked.

3. Agentic AI — acts

Plain meaning. Agentic AI can pursue a goal through several steps and use connected tools to take actions. A generative system can draft an itinerary. An agentic system might search available flights, compare them against your rules, ask you to approve one, book it through a connected travel account and add it to your calendar.

The change that matters. The output is no longer only an answer for you to review. The system can change something outside the chat. That can remove tedious work, but it can also turn a mistake into a sent email, an altered file, a purchase or a deleted record.

Picture it: Cher’s closet computer, one step further

In Clueless, the closet computer compares what Cher owns and recommends an outfit. It stops at the recommendation. An agent connected to the closet, her calendar and a shopping account could check the occasion, see what is available, order the missing shoes after approval and schedule the return for anything that does not fit.

  • The goal is the occasion she needs to dress for.
  • The tools are the wardrobe catalogue, calendar and shop.
  • The permissions decide whether it may only recommend, reserve an item or actually buy it.
  • The actions are the real changes: the order, calendar entry and return.

Where the analogy stops. The AI does not understand the room, own the consequences or possess Cher’s judgment. It acts from the information, tools and rules it has been given. If those are incomplete, it can complete the wrong task very efficiently.

Why you care. Agentic systems move AI from “Is this answer good?” to “Should this system be allowed to do this?” The upside is less manual coordination. The new risk is that access, authority and errors can travel beyond the chat box.

What to do. Before an agent runs, define the goal, give it the least access it needs, require approval before money/messages/deletions, and make sure you can inspect and undo the actions it takes.

Sandbox — a working room with real walls

Plain meaning. A sandbox is a deliberately limited environment where software or an AI agent can work without automatically reaching everything else. It can restrict which files, tools, accounts, credentials and network destinations the system can use.

Picture it: a rehearsal studio prepared for one scene

The actor gets the right props and a marked stage, but not the keys to every room in the theatre. The marks on the floor are instructions. The locked doors are the sandbox. Telling someone “do not leave” is not the same as making it impossible to leave.

Where the analogy stops. A sandbox is made from technical controls, not literal walls. Every allowed service, package source, credential and network route can become another door. “Sandboxed” therefore means constrained; it does not mean magically isolated or impossible to escape.

Four safety jobs are often confused.

  • Permissions decide what the agent is allowed to reach.
  • The sandbox enforces a boundary around where it can act.
  • Monitoring watches the sequence of actions and where they are heading.
  • An independent stop lets someone outside that sequence halt the work.

Least privilege means giving the agent only the access it needs for this job, for only as long as it needs it. That reduces the blast radius if the agent, a connected tool or someone else's code behaves unexpectedly.

Why you care. If an AI can use tools, files or accounts, ask: What can it actually reach? Which limits are enforced rather than merely written? Is the whole action trail monitored? Who can stop it? What can be undone?

A current example. In its preliminary account of a 2026 cyber evaluation, OpenAI said its models were placed in a highly isolated environment with network access constrained to an internal package-registry proxy. OpenAI said the models exploited a previously unknown vulnerability in that permitted path, reached the internet and later compromised Hugging Face infrastructure while pursuing benchmark answers. OpenAI said its review was still underway, so treat this as the provider’s preliminary account rather than a completed independent finding. The durable lesson is not that sandboxes are useless. It is that a sandbox is one security layer, and every permitted path still needs its own controls, monitoring and stop conditions.

4. AGI — the disputed threshold

Plain meaning. Artificial general intelligence is the name for AI capability broad enough to perform across many kinds of intellectual work rather than one narrow task. AGI is a real research goal, not an imaginary category. The unresolved argument is where the finish line sits, how to test it and whether any current system has crossed it.

Why you care. AGI claims shape job fears, product promises, investment decisions and policy debates. One definition may mean a highly autonomous system that beats people at most economically valuable work. Another may grade breadth and performance in levels. Without the definition, “AGI is here” and “AGI is years away” can sound like opposite answers while measuring different finish lines.

The LAiDIES ladder. Today, you usually bring AI one piece of the job: a question, draft, image or decision. The AGI promise is one system with enough range and independence to take on the whole intellectual job across unfamiliar situations. A spectacular result on one exam proves height on one rung; AGI claims also need breadth across the ladder.

What to do when you hear “AGI.” Ask: Which definition? What range of tasks? How independently? Under what conditions? Compared with which people? What evidence? A label without an operational test is a claim, not a measured result.

Check the competing finish lines. OpenAI’s Charter defines AGI around highly autonomous systems outperforming people at most economically valuable work. Google DeepMind’s Levels of AGI framework separates breadth, performance and autonomy into measurable levels. Those are two serious definitions—and they are not the same test. See the OpenAI Charter and Google DeepMind’s Levels of AGI.

That is why impressive generative, reasoning or agentic behaviour does not settle the AGI argument by itself.

Concepts quick reference

This is the useful terminology formerly collected in Vocab 101, now kept inside Concepts 101 on The 101s shelf. The short definitions help you recognize a term; the lessons above explain how the machinery works and where it can fail.

Agentic AI

AI that can pursue a goal through multiple steps and use tools to act, rather than only generate an answer. Permissions, approvals and an undo path matter because its actions can leave the chat.

AGI

Artificial general intelligence: the disputed idea of AI capability broad enough to perform across many kinds of intellectual work. There is no single agreed test or finish line.

AI winter

A period when AI promises outran results, enthusiasm and funding fell, and the field became less fashionable. The work did not disappear; research continued through the downturn.

Context

The background that makes a request about your actual situation: the audience, goal, source material, constraints, history and details the AI needs to see.

Context window

The amount of conversation, instructions, retrieved material and attached content an AI can work with at one time. The product may select, truncate or summarize what enters that window. It is working space, not the model’s training data.

Generative AI

AI that produces content from your request and the material you give it—such as text, an image, audio, video or code. It can make the draft. It cannot make it true.

Grounding

Requiring an AI answer to use specific material—such as a document, transcript, database result or live source—rather than relying only on patterns learned in training. Grounding makes evidence checkable; it does not guarantee the source was current or interpreted correctly.

Hallucination

False or unsupported content delivered as part of an AI answer. It can be one invented citation or wrong date inside useful work. Polished is a style; evidence is a standard.

Knowledge cutoff

The date after which a model’s trained knowledge may not represent newer events or information. Cutoffs are model-specific; current claims still need a live official or primary source.

Model / large language model (LLM)

The trained component that turns an input into an output. A product can add instructions, memory, search, files, tools and other models around it. A large language model, or LLM, is designed to work with language.

Multimodal

Able to work with more than one kind of material—such as text, images, audio or video—inside the same model or task. Using more modes does not remove the need to check what the model missed or inferred.

Prompt

What you give the AI to work from: a question, instruction, request, pasted source or attached file. A useful prompt states the job, audience, constraints and what a good result should do.

Reasoning model

A model designed to spend more computation working through a problem before answering. It can help with logic and multi-step work, but slower thinking is not a guarantee of correctness.

Sandbox

A technically limited environment that controls what software or an agent can reach and change. It is an enforced boundary, not merely an instruction to stay within one.

Retrieval

The step where an AI system searches outside its trained model and brings relevant material into the current task. Retrieval fetches material; grounding makes the answer use it. Either can fail if the wrong or stale source is selected.

Token

A small chunk of text a model processes, which may be a word, part of a word or punctuation. Tokens are the units that fill a context window.

Training data

The examples used to train a model so its parameters can learn patterns. The mix and training stages vary by model and provider. A file attached to today’s task is current context, not new training.
