# Build-completion policy

**Status:** STANDING PORTFOLIO AND RELEASE CONTROL
**Applies to:** every Ali-approved intended LAiDIES experience, capability,
integration and cross-page result

An incomplete intended capability is a build obligation. Hiding it, relabelling
it as a smaller product or narrowing the public promise does not complete the
work and is not an accepted destination.

## Allowed dispositions

- **BUILD BEFORE LAUNCH** — implement, integrate, independently verify and bind
  the complete intended user result to the release.
- **BUILDING** — implementation is active; owner, dependencies, current proof,
  next test and completion contract are recorded.
- **BLOCKED — BUILD REMAINS REQUIRED** — an external credential, provider,
  spending/data authority or irreducible decision prevents progress; name the
  blocker, owner and immediate unblock action.
- **OWNER DECISION REQUIRED** — Ali's product, mission, public-identity or
  material trade-off ruling is genuinely necessary before the correct build
  can be selected.
- **DECLINE/REMOVE FROM INTENT** — allowed only when Ali explicitly decides the
  capability is no longer part of the product, with the superseding decision
  recorded.
- **INTENTIONAL LATER RELEASE** — the capability is deliberately staged
  outside the current release, with its approved release/milestone or objective
  trigger, product reason, owner, dependencies, build contract and acceptance
  evidence recorded. If it was previously part of the current launch promise,
  moving it later requires Ali's explicit decision.

`HIDE/LABEL FOR LAUNCH` is superseded as a completion disposition.

## Intentional later-release test

Later release is valid only when all of these are true:

- the product specification or a new explicit decision says it belongs to a
  later named release/milestone or objective trigger;
- the reason is deliberate product sequencing—not missed work, lack of time or
  a desire to make the current checklist pass;
- it has an owner, dependency path, build packet trigger and definition of
  done;
- the current experience does not display a fake, dead or success-shaped
  version of it;
- current launch claims and navigation do not imply that it is available; and
- Control Room tracks it as planned scope until its release trigger fires.

A feature that simply failed to finish remains **BUILDING** or **BLOCKED —
BUILD REMAINS REQUIRED**. It does not become intentional later scope
retroactively.

## Temporary safety controls

A broken, unsafe, privacy-sensitive, costly or misleading control may be
temporarily disabled, held or hidden while the build proceeds. That action:

- prevents user harm or a false claim;
- does not close, downgrade or defer the build obligation;
- keeps the item **BUILDING** or **BLOCKED — BUILD REMAINS REQUIRED**;
- names the owner, missing work, unblock condition and retest;
- may not be used to call the building complete or ready; and
- must be removed when the verified implementation replaces it.

Truthful status and error copy remains required inside the finished product.
That is product behavior—not a substitute for implementing the capability.

## Completion evidence

“Built” requires the complete intended journey: frontend, backend/service,
authoritative state, every producer and consumer, visitor-state transitions,
failure/retry/idempotency, update/delete/revoke/refund, privacy/security,
accessibility, analytics where required, exact release binding and the
appropriate local and public verification. A partial local alternative cannot
lend completion to the intended account-backed, cross-device, delivered,
moderated, rewarded or public result.
