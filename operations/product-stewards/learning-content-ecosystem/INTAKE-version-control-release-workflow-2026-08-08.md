# Learning intake — version control and the path from work to public

**Status:** CAPTURED / NOT BUILT / NOT ADMITTED / NOT PUBLIC

**Ali decision — 2026-08-08:** The explanation of Git, commits, pushes and deployment should become a connected LAiDIES learning pathway. It should begin with a short explanation when the vocabulary first appears, expand into a more advanced LIBRAiRY book, and support a practical Sunnyvaile High class covering best practices.

## Learner job

Understand what happens between changing a file and making a safe public release, so a non-technical professional can work intelligently with Codex or another coding agent without treating “saved,” “committed,” “pushed,” “deployed” and “live” as synonyms.

This is broader than Codex. Git is a version-control system used with many coding tools and ordinary human development workflows. A regular chat does not normally edit a project or use Git unless it has agent/tool access to those files and commands.

## One concept, three complementary surfaces

### 1. In-context 101 explanation

Use a short plain-English explanation the first time the terms appear in beginner material. Its job is vocabulary and orientation only:

- saving updates the working file;
- committing creates a named checkpoint in the project's history;
- pushing copies committed checkpoints to the shared remote repository;
- deploying turns a selected version into a running website or service;
- public verification confirms what visitors actually receive.

Do not turn the 101 explanation into a full software-development course.

### 2. Advanced LIBRAiRY book

Teach the connected system from working files to a safe release. The reader should understand:

- working files, repository, Git and history;
- saved versus committed versus pushed versus deployed versus publicly verified;
- why small meaningful commits help recovery, comparison and collaboration;
- branches and shared work in plain language;
- reviewing exactly what changed before committing;
- keeping unrelated work out of a commit;
- resolving conflicting changes without losing work;
- when to commit, when to push and why pushes are usually less frequent;
- testing before release;
- release identity, rollback and recovery;
- how AI coding agents fit into the workflow, including what they can and cannot prove.

Working title is deliberately **unlocked** until the book's reader question, scope and catalogue fit are reconciled.

### 3. Practical Sunnyvaile High class

Let the learner practise the workflow on a small, harmless project. The class should produce observable skills, not repeat the book:

1. change and save a file;
2. inspect the change;
3. make one clear commit;
4. make a second change and compare the checkpoints;
5. push to a safe shared location;
6. review before deployment;
7. deploy a bounded practice version;
8. verify the live result;
9. recover from an intentionally introduced mistake without destroying other work.

Best-practice extensions may include commit scope and messages, branches, pull requests/review, merge conflicts, automated checks, secrets and private data, safe rollback, collaboration with coding agents, and the difference between local success and public truth.

## Product boundary

- The book supplies the durable mental model and reference.
- The class supplies guided practice and feedback.
- The 101 explanation prevents unexplained jargon.
- None of the three should duplicate the others word-for-word.
- Do not assume every learner wants to become a developer; frame the value as control, recoverability, collaboration and informed approval of AI-assisted work.
