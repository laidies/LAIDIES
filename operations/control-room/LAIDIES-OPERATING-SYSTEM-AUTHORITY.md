# LAiDIES operating-system authority for independent review

Evidence date: 2026-08-02

Status: **CURRENT REVIEW AUTHORITY — DESIRED MODEL PLUS VERIFIED GAPS**

Purpose: give an independent reviewer one bounded description of what LAiDIES
is trying to operate, what is already evidenced, what is only documentary, and
what must be enforced before the system can be trusted.

This file does not declare the operating system complete. It is the authority
for reviewing and improving it. Where an older brief, handover, generated
artifact or increasing version number conflicts with this file, the current
working agreement, the active-work ledger, an admitted asset registry or Ali's
newer explicit direction, the older material is historical and cannot be used
as authority.

## Outcome

LAiDIES must work as a one-woman, human-in-the-loop product and media company:

- agents own defined buildings, products and shared systems;
- production moves without Ali manually dispatching every mechanical step;
- Ali receives only real taste, mission, identity, spend and irreversible
  publication decisions, in a concise mobile-friendly inbox;
- no work disappears, silently stalls, loops indefinitely or becomes “done”
  because an agent wrote a confident report;
- current brand, canon, facts, visitor promises and approved assets are used;
- old/rejected material is not selectable by builders;
- multiple non-colliding lanes can run in parallel;
- every public claim is traceable from source through build, review, release
  identity and public verification;
- quality controls preserve LAiDIES' writing, teaching, visual, accessibility,
  technical-accuracy and freshness standards without overengineering work that
  does not affect the required outcome.

## Authority order

Use the first applicable source in this order:

1. Ali's newest explicit direction for the exact product or decision.
2. `operations/CODEX-WORKING-AGREEMENT.md`.
3. `operations/ACTIVE-WORK.md` and `operations/engine/LEDGER.md`.
4. Machine-readable current registries and checksum-bound accepted receipts.
5. Current product dossier, canon, writing lock, building brief and state file.
6. Historical handovers, explorations and generated artifacts as evidence only.

No filename containing `final`, `approved`, `master`, `v2` or a higher version
number establishes authority. Search results are discovery, not admission.

## Fixed truth vocabulary

Plans, local files, reviews, deployments and public results are different
states. Use the fixed status vocabulary in the working agreement. In
particular:

- a plan is not built;
- built locally is not accepted;
- accepted is not deployed;
- deployed is not publicly verified;
- a visible widget is not proof that its provider journey works;
- a backend projection is not a completed visitor experience;
- `RUNNING` is invalid without a live task identity and recent heartbeat.

## Portfolio and ownership model

The product registry currently describes 67 products across 17
building/function groups and a larger guild of specialist roles. Preserve that
domain ownership, but execute through five reusable roles:

1. **Accountable product/building owner** — owns purpose, visitor journeys,
   backlog, integration, release readiness and post-release health.
2. **Bounded maker** — writes only within an explicit non-colliding scope and
   returns exact artifacts and tests.
3. **Evidence support** — read-only inventory, research, extraction and
   diagnostics; cannot approve its own subject.
4. **Independent judge** — evaluates the exact immutable artifact against the
   brief and calibrated rubric; cannot repair the artifact it judges.
5. **Release verifier** — binds accepted inputs, release identity, deployment
   identity and public proof; cannot convert a local candidate into authority.

Specialists for voice, teaching, facts, brand, accessibility, security,
platform, growth, revenue and media collaborate with the accountable owner;
they do not replace that owner or create competing product lanes.

Ownership is operational only when each required area has all of the
following: a named accountable owner, a callable/configured agent or task, an
event trigger or schedule, an allowed write scope, a live task/heartbeat when
running, a required output artifact, an independent acceptance owner, a
handoff destination and a next-run/recheck rule. A role name in a registry or
Markdown file without this execution chain is **DOCUMENTARY**, not assigned
work.

The complete coverage matrix must map to executable ownership. Unassigned rows
become launch/build tasks; they cannot be closed by writing another plan. The
Control Room must be able to prove which owners are idle by design, queued,
actually running, waiting on a dependency, blocked, awaiting Ali, accepted or
released.

## Mandatory production flow

Every material task follows this sequence:

1. **Capture** — one canonical task record with purpose, visitor/user outcome,
   product owner, acceptance owner, dependencies, scope and priority.
2. **Resolve prerequisites** — current canon, facts, approved assets, copy,
   service boundaries and target surfaces are enumerated and admitted.
3. **Brief** — requirements are specific enough to build and test. It states
   what must be shown, taught or accomplished, not merely a mood.
4. **Pilot** — the smallest representative proof is built first. For video this
   includes identity, wardrobe, location, narration-picture fit and meaningful
   motion before a full render. For pages it includes representative desktop
   and mobile states before a whole-site batch.
5. **Maker build** — only after the pilot passes. Inputs and outputs are
   checksum-bound where substitution risk matters.
6. **Deterministic checks** — existence, counts, allowlists, links, captions,
   responsive overflow, source coverage, state transitions and other
   machine-testable requirements fail closed.
7. **Independent review** — perceptual, semantic, teaching, voice and UX
   requirements receive genuine artifact review, not self-attestation.
8. **Integration** — the product owner verifies the result in its real visitor
   journey and related surfaces.
9. **Ali decision** — only when taste, mission, public identity, spend or an
   irreversible/public choice genuinely requires her.
10. **Release and public verification** — exact commit/artifact/deployment and
    real public journeys are bound in one receipt.
11. **Learning scan** — reusable failures and successes update the prevention
    ledger and, where appropriate, Behind the Build.

An agent may not skip directly from brief to full batch, from local artifact to
Ali review, or from accepted candidate to public claim.

## Rules must be enforceable

Instructions shape work; deterministic checks enforce objective rules. Any
objective requirement that has failed twice must become one of:

- an allowlist/registry admission check;
- a schema or count assertion;
- a scoped lint/test;
- a builder preflight;
- a release manifest check;
- a bounded lifecycle hook.

Hooks must be deterministic, fast and loop-safe. They must not pretend to judge
subjective quality. Subjective quality requires an artifact, a rubric and an
independent human or calibrated model review. A checkbox or a receipt saying a
review happened is not evidence that the artifact was actually inspected.

## Asset and canon safety

Builders consume only explicitly admitted current-generation inputs. The
active asset registry is the beginning of this enforcement, not proof that all
assets are resolved.

- `ACTIVE` entries may be used within their declared role.
- `UNRESOLVED` entries block dependent production.
- retired, rejected, historical, superseded and unadmitted files are not
  eligible build inputs even if physically present.
- references must bind exact file identity when identity, wardrobe, location,
  wordmark, map, title card, credits or episode continuity matters.
- an asset may be retained as historical evidence without remaining searchable
  to builders as a valid candidate.

The current media failure fixtures include: retired wordmark, wrong heroine,
wrong outfit, false/old town map, invented characters, MAiVENS represented as
town characters, overlay captions, caption casing errors, static slideshow in
place of required motion, rectangular light-box overlays and missing
environmental animation. These must become reusable preflight/evaluation
fixtures, not merely prose in a postmortem.

## Anti-stall and stop-loss

Every active task requires a task ID, owner, acceptance owner, write scope,
start time, heartbeat, current artifact and exact next action. A generated
dashboard must expire `RUNNING` when those facts are not current.

- Attempt 1 may repair the artifact.
- Attempt 2 must identify why the first correction failed and change the
  brief, inputs, fixture or tool chain.
- A third materially similar failure cannot start another full batch. It
  escalates with one decision-ready diagnosis and smallest unblock.
- A blocked task remains owned, has a concrete unblock action and a scheduled
  recheck. `BLOCKED` is not an archive.
- A judge may return work to the maker once; repeated maker/judge cycling must
  return to the accountable owner for root-cause correction.

## Parallelism and model use

Parallelize work that is independent and read-heavy or writes to disjoint
artifacts: research, inventories, source verification, separate building
owners, separate asset generation and independent reviews. Keep dependent
pipeline stages sequential. Never allow multiple agents to edit the same page,
registry, release manifest, stylesheet or master concurrently without isolated
worktrees and an explicit integration owner.

Use the least expensive model/reasoning configuration that can reliably meet
the task. Multi-agent complexity must earn its cost through faster delivery or
better evidence; it is not a goal by itself.

## Ali's Control Room

The Control Room must be generated from canonical state, not maintained as
several handwritten dashboards. It must work on laptop and phone and show:

- **Needs Ali now** — a small queue with the exact artifact, decision, options,
  recommendation, consequence and deadline;
- **In progress** — live task identity, owner, heartbeat and next artifact;
- **Blocked** — owner, blocker, unblock action, next recheck and escalation;
- **Ready to release** — exact accepted identity and remaining release steps;
- **Released/publicly verified** — commit, deployment, public proof and
  rollback target;
- complete portfolio inventory, site health, agent health, freshness,
  scheduled releases, analytics, sign-ups, content/social pipeline and ranked
  recommendations.

Ali must not be asked to discover objective defects, copy hashes, diagnose
builders, reconcile status ledgers or decide between options that have not
passed prerequisites.

## Building and visitor-experience ownership

Every building owner is responsible for the building page, its subpages and
the real experience inside it. Each must test at least:

- first-time visitor;
- returning visitor who is not a resident;
- resident who is signed in;
- returning resident who is not signed in;
- mobile and desktop;
- empty, loading, error, offline/provider-unavailable and recovery states.

Pages must feel like visiting the named building in the same SUNNYVAiLE world,
while remaining intuitive, accessible and efficient. Avoid generic card grids,
boxes inside boxes, endless scrolling and invented state. Navigation must be
consistent, preserve a sensible return path and expose useful destinations
without burying them behind unnecessary layers.

## Content and learning ecosystem

Episodes, study packs, quizzes, classes, library records, NewsStand stories,
Promptoscope, practical AI tips, career guidance, songs and community prompts
have different jobs but one learning system. Before release, content must be:

1. technically accurate and supported by authoritative/current sources;
2. fresh enough for the claim and feature;
3. written in the LAiDIES voice without condescension, generic empowerment or
   AI slop;
4. appropriate in depth, structure and interaction for its destination;
5. clear about why the concept matters, how it works, where it appears in real
   life and how it connects to other concepts;
6. supported by worked examples, counterexamples, mental models and useful
   practice where the format calls for them;
7. reconciled against related content so the site does not contradict itself;
8. indexed, searchable and linked to the most relevant episodes, classes,
   library entries, articles, tips and tools;
9. evaluated for useful derivatives: Daily Buzz, Promptoscope, social,
   activities, a song or other memory device—without duplicating the same
   content everywhere.

Freshness/intake agents may identify opportunities from AI Daily Brief,
Ethan Mollick, official vendor sources and other vetted voices. Discovery must
route to an owned build task with a clear product fit; a recommendation alone
is not progress. No derivative advances until the underlying source and public
release identity are verified where required.

## Social media and audience engine

Social is an owned production and learning system, not a folder of prepared
graphics. Its canonical state must keep these truths separate for every unit:
`IDEA`, `BUILT`, `REVIEWED`, `APPROVED`, `SCHEDULED`, `PUBLISHED` and
`PUBLICLY VERIFIED`. A local image, caption or calendar entry is not a post.

The engine must cover:

- current platform and audience research, including evidence-based format,
  hook, retention, accessibility and engagement practices rather than generic
  “viral” folklore;
- a coherent pre-opening and ongoing editorial calendar across Instagram,
  LinkedIn, YouTube and any other admitted channel;
- original LAiDIES concepts and source-vetted idea intake without copying
  creators' expression;
- channel-native scripts, captions, carousels, short video, thumbnails,
  alt text, metadata, music/rights checks and approved visual identity;
- episode, NewsStand, class, library, KSVL, Behind the Build, practical-tip,
  career-tip, Town Group Chat and uplifting-but-not-cringe content families;
- launch/release derivative triggers only after the exact underlying content
  identity is accepted and, where necessary, publicly verified;
- a complete posting runbook: timing, first comment when supported by current
  evidence, community replies, moderation, escalation and follow-up—not only
  creation of the initial post;
- Ali review only for real taste/public-identity decisions, with complete
  ready-to-post packages rather than asking her to make content herself;
- privacy-safe analytics, attribution, experiments and a measured learning
  loop that changes future content without confusing unknown data with zero;
- ownership of provider accounts, scheduler/tool subscriptions, permissions,
  renewal/cost, credentials boundary, failure fallback and export/exit plan;
- content rights, provenance and reuse boundaries that preserve ordinary
  sharing while discouraging unattributed commercial copying.

The existing Audience & Growth records currently report a bank of built units
but zero ready and zero published. Treat that as a state to reconcile, not as
evidence that the engine is operational. The independent audit must identify
which research, generation, review, scheduling, publication, public
verification, engagement and measurement steps are executable and which are
only planned.

## Revenue and content protection

Revenue work remains an owned lane even before monetization is activated.
Building designs should preserve clean future entitlement, inventory, reward,
fulfilment and analytics boundaries without falsely presenting commerce as
live. Butterfly clips, FAiRY uses, rewards, charms, Closet ownership, trading
cards, classes, book-fair ideas and membership benefits require an auditable
ledger and explicit economic rules before paid conversion.

Protect content through clear copyright/terms, provenance, controlled source
access, appropriate watermarking/metadata, platform rights controls and
monitoring. Do not damage accessibility or ordinary sharing, and do not claim
technical prevention can make public media impossible to copy.

## Repository and worktree discipline

- Keep source, compact evidence, manifests and receipts in Git.
- Keep generated intermediates out of ordinary source paths.
- Evaluate Git LFS or object storage for large collaboratively versioned media.
- Do not rewrite history or wipe a dirty tree without a verified backup and
  migration plan.
- Every bounded accepted batch gets an intentional exact-path commit and push.
- Generated artifacts must identify their source manifest and builder.
- Historical material should be moved behind explicit archival boundaries or
  excluded from builder discovery; do not delete evidence merely to make
  search cleaner.

## Overengineering test

Before adding a task, gate, agent or document, ask:

1. Which required outcome or recurrent failure does this change protect?
2. Is there a smaller deterministic check or clearer brief that achieves it?
3. Does it replace an existing mechanism, or create another competing source?
4. What evidence will show it saved time, improved quality or reduced risk?
5. Can it be deferred without making the visitor promise false or the work
   harder to change later?

Do not repeat provenance investigations for work already known to be original,
produce full films before representative motion/identity proofs, or create
process artifacts that nobody reads and no executable check consumes.
