# Chapter 1: Your first useful ChatGPT job

*How to choose the right place, model and effort — then catch the mistake before anyone else does*

**Product facts checked: 2 September 2026**

ChatGPT changes quickly. If a button or plan in your account looks different,
believe the account in front of you. The method in this chapter still works:
give the tool a clear job, reliable material, sensible boundaries and a result
you can actually check.

## The reunion invitation with two Saturdays

You are helping with a Class of 2002 reunion. The approved organiser's note says
the party is on **Saturday 17 October 2026**. The old invitation says **Saturday
10 October**. The tiny website has the new date in its heading, but the old one
is still tucked into the page title.

Nobody wants to send an apologetic “please ignore the first invitation” email to
eighty former classmates. This is exactly the sort of ordinary, fiddly job
ChatGPT can help with — and exactly the sort of job where a polished answer can
hide one stubborn mistake.

The shortest useful advice is this:

> Start in the simplest place that can finish the job. Give it one source of
> truth. Tell it what must not change. Then inspect the actual result, not the
> little message announcing that the work is complete.

We will do the whole job in this chapter. Along the way, you will learn what
Chat, Work and Codex are for, how to choose a model and effort level, what to set
up once, and what still needs your eyes whether you pay for ChatGPT or not.

The reunion and all its files are fictional. The example is a constructed
teaching demonstration, not a transcript from somebody's account.

## First, make ChatGPT feel less like somebody else's computer

You do not need an elaborate setup before your first useful task. Five minutes
is plenty.

Open **Settings** from the desktop app menu. On a Mac, you can also press
**Command-comma**; on Windows, **Control-comma**. The exact menu can vary by
surface and account, but these are the choices worth understanding.

### Personality: how it speaks, not how well it thinks

Personality changes the way ChatGPT communicates. Friendly may feel warmer;
Pragmatic may get to the point faster. It does **not** make the model more
capable or more accurate.

Choose the style you find easiest to work with. You can still ask for a
different tone in an individual chat.

### Custom instructions: the things that stay true

Use custom instructions for preferences that should travel from one chat to the
next. For example:

```text
Use Canadian English. Write for an intelligent reader with no technical
background. Lead with the practical answer. If information is missing, name it
instead of inventing it. When you create or revise something, tell me what you
checked and what remains uncertain.
```

Do not put this reunion's date in your permanent instructions. Current facts
belong with the current job. Otherwise October's reunion may wander into
December's holiday newsletter like a guest who refuses to leave.

### Memory: helpful background, not the filing cabinet

Memory may help ChatGPT retain useful background, but do not rely on it for a
deadline, an approved price, a private rule or the only copy of an important
instruction. Put must-follow facts in the prompt or in a maintained source
file.

If you use Codex regularly, its durable personal instructions can live in a
global `AGENTS.md` file. You do not need that for this chapter; we will return to
rules and context files later in the guide.

### Projects: one home for work that continues

Create a Project when a job will last across several chats or has a set of
related files and instructions. A Project can keep those materials together. A
Project on the web does not automatically see a folder on your computer: you
must upload or connect the material you want it to use.

For a one-off question, a normal chat is fine. For the reunion, a Project would
be sensible if the invitation, website, photo captions and follow-up messages
will evolve over several weeks.

Before adding real files, check your organisation's rules and your Data
Controls. Remove information the job does not need. Our exercise deliberately
keeps the private RSVP list out of the source pack.

## Four choices that sound like one

When someone says, “Which ChatGPT should I use?”, she may be asking four
different questions.

| Choice | What it changes | The question to ask |
| --- | --- | --- |
| **Model** | The engine doing the thinking | Is this repeatable, everyday or genuinely complex work? |
| **Effort** | How much reasoning time the model may spend | Has the task earned more time, or is it already clear and bounded? |
| **Surface** | Where the work happens and what it can act on | Do I need words, a finished file or changes to code? |
| **Plan** | Access, capacity and available controls | Can my current account complete this route within its limits? |

The model is the engine. Effort is how long you let it work the problem. The
surface is the workshop it can work inside. Your plan is the allowance that
governs access and capacity.

That picture is useful only up to a point. A bigger engine, more time or a paid
allowance does not turn a rumour into a fact. Good source material and human
inspection still matter.

## Chat, Work or Codex?

Choose by the result you need, not by which name sounds most impressive.

### Use Chat when the result is mainly words or thinking

Chat is the easiest place to ask a question, explore options, compare supplied
material or draft text through a conversation.

For our reunion, Chat can compare the organiser's note with the old invitation,
list conflicts and write corrected copy. You then make the changes yourself.

### Use Work when you want a reviewable result or file

Work is for delegating a more complete job: a brief, analysis, workflow,
document, deck or other file you can review. Depending on your account and
environment, it can use uploaded files, plugins and approved tools. Local Work
is useful when the task needs files or applications on your computer; cloud
Work can continue away from the computer and be resumed from web or mobile.

For our reunion, Work is the natural choice if you want a finished invitation
document or PDF rather than copy to paste.

### Use Codex when the job is the website itself

Codex is the developer-oriented surface. It can work with code and files, run
commands and tests, and report exactly what changed. You do not have to become
a programmer to ask it to repair a small website, but you do need to tell it
which folder it may change and what proof you expect.

For our reunion, Codex is the right choice when the old date must be found and
replaced in the actual website files, followed by a check of the page.

These surfaces overlap. Chat can help write code; Work can create files; Codex
can explain something. The distinction is not “least clever to most clever.” It
is how much context and action the job requires.

**For this job:** use Chat to reconcile the facts and approve the public copy,
Work if you want the invitation produced as a file, and Codex if you want the
website files changed and tested. You may use only one route if that is all the
job needs.

## Which model should you pick?

If your account does not show a model picker, use the model it provides. Do not
spend twenty minutes searching for a menu that is not part of your plan or
surface.

If you do have a choice, OpenAI's current line-up has four practical starting
points. The newest name is not automatically the right answer:

| Model | Reach for it when… | Reunion example |
| --- | --- | --- |
| **Luna** | The instructions are clear, the pattern repeats and speed or volume matters. | Extract every date, time and RSVP instruction from a folder of invitations. |
| **Terra** | You need a capable everyday all-rounder for a well-bounded job. | Compare three sources, explain the conflicts and draft corrected copy. |
| **Sol** | The job is demanding and professional, and depth or polish may reduce meaningful repair. | Reconcile contradictory committee notes, preserve a distinctive voice and propose a defensible final package. |
| **Astra** | The work crosses several systems or disciplines, carries a long context, or needs tools and deeper synthesis to stay coherent. | Reconcile years of event records, update the site and invitation pack, coordinate independent research, and verify that every public version agrees. |

**Our starting choice:** Terra, if it is available, because the source hierarchy
and output are clear but the job needs more judgment than mechanical extraction.
If Terra is not in your picker, use the model your account provides. This small
reunion job does not become an Astra job merely because Astra is newer.

Do not treat this table as a permanent ranking. Model families and defaults
change. More importantly, a smaller model with a crisp job and clean source pack
can outperform a larger model asked to guess what you meant.

Astra earns its place when its extra synthesis can change the outcome. If you
use it for a long job that can take several steps or use tools on your behalf,
add four boundaries that a small chat may not need:

```text
Authority: the signed event brief wins over meeting notes and old pages.
Autonomy: continue with reversible in-scope work; stop for publishing, spending,
deletion or a real change of scope.
Delegation: split independent research and checking when that saves time, but
keep one owner for each final file.
Testing: check the changed journey and its real dependencies. Stop when those
checks pass; do not widen this into a general audit.
```

Why be this explicit? OpenAI's current Astra guidance says it can be sensitive
to long instruction stacks, may stop for a focused question, may not delegate
enough and can test a small task more thoroughly than it needs. The boundaries
do not make it infallible. They tell a powerful worker what finished means.

## How much effort should you choose?

Effort is not the difficulty of the subject in some grand universal sense. It
is the amount of reasoning the task has earned.

Start low when the job has one clear source, a predictable output and an obvious
check. Increase effort when there are several sources to reconcile, linked
consequences to trace, competing constraints to balance, or a lower setting has
failed in a specific way.

| Effort | Good use | What to watch |
| --- | --- | --- |
| **Light** | Quick, well-scoped work: extract, format, classify or make one obvious edit. | It may not trace subtle dependencies unless you name them. |
| **Medium** | The best everyday starting point when the task needs some judgment. | Still inspect the result; “medium” is not a confidence score. |
| **High** | Several steps, sources or trade-offs must be considered together. | More reasoning can produce more commentary and review than a small job needs. Define the finish line. |
| **Extra High** | The same kind of demanding work, with more room for a careful pass. | Use it because the task has earned it, not because the label sounds reassuring. |
| **Max** | One unusually hard task deserves considerably more time. It may need to be enabled. | It is slower and unnecessary for routine work. Give it a tight brief or it may explore far beyond the useful answer. |
| **Ultra** | The job contains genuinely separable workstreams that can be handled by subagents. | Most tasks do not need it. It can create extra coordination and review work if the job is really one small thread. |

For our three-source reunion check, **Medium** is enough. Move to High if the
committee supplies six contradictory versions, or if Medium demonstrably
misses linked occurrences after a clear prompt.

High effort is a setting, not a tiara. The useful question is not whether the
job feels important. It is whether extra reasoning is likely to improve the
result: deeper synthesis, more linked constraints, or a specific failure at a
lower setting. Without a clear finish line, higher effort can buy more
commentary and review rather than a better answer.

The exact effort menu depends on the model, plan and surface. Eligible ChatGPT
Power accounts currently show combinations including Terra Light, Sol Light,
Sol Medium, Astra Light, Astra Medium and Astra Extra High. Other options can
be absent. If you use the API later, Astra has a different list—`low`, `medium`,
`high`, `xhigh` and `max`—and does not accept `none`. API **Pro execution mode**
is also a technical service option; it is not the same thing as buying a
ChatGPT Pro subscription.

## Now do the job

Here is the complete source pack.

### Source 1 — approved organiser's note

```text
APPROVED PUBLIC DETAILS — 1 SEPTEMBER 2026

Class of 2002 Reunion
Saturday 17 October 2026
7:00–11:00 p.m.
Starlight Roller Rink
RSVP by 15 September using the public RSVP link.

Do not publish anyone's email address, phone number or RSVP status.
This note overrides earlier invitations and web copy.
```

### Source 2 — old invitation

```text
CLASS OF 2002: ONE MORE NIGHT UNDER THE DISCO BALL

Saturday 10 October 2026
Doors at 6:30 p.m. · Starlight Roller Rink

Dig out the butterfly clips. Leave the dial-up modem at home.
RSVP by 15 September.

Footer: See you Saturday 10 October.
```

### Source 3 — website extract

```html
<title>Class of 2002 Reunion — October 10</title>
<h1>One more night under the disco ball</h1>
<p>Saturday October 17, 2026 · 6:30–11:00 p.m.</p>
<a href="https://example.test/rsvp">RSVP by September 15</a>
```

### Deliberately excluded

The private RSVP spreadsheet contains names, email addresses, phone numbers and
attendance status. None of that is needed to correct public dates and times, so
it is not uploaded, pasted or connected.

Notice what the organiser's note does: it names itself as the source of truth
and says it overrides the older material. Without that hierarchy, ChatGPT would
have to guess which date won.

## The prompt

This is not a magic formula. It is simply a useful brief in ordinary language.

```text
Help me correct the public materials for a fictional Class of 2002 reunion.

GOAL
Produce approved invitation copy and a website change list. Both must match the
approved organiser's note.

SOURCE OF TRUTH
The organiser's note overrides the old invitation and website extract. If the
sources disagree, use the organiser's note and list the conflict.

OUTPUT
1. A short discrepancy table covering every date, time and RSVP instruction.
2. Complete corrected invitation copy, including its footer.
3. An exact list of website text or code values that must change.
4. A final verification table showing the approved value and every place where
   it should appear.

BOUNDARIES
- Preserve the invitation's friendly Class of 2002 tone unless it conflicts
  with the approved facts.
- Do not invent a price, dress code, contact person or extra event.
- Do not request or expose names, email addresses, phone numbers or RSVP status.
- Do not say the job is complete unless every public occurrence in the supplied
  material has been checked.

Before finishing, search your own proposed output for “October 10”, “10 October”
and “6:30”. If any remain, either correct them or explain why they are retained.
```

The goal says what success is. The source hierarchy prevents a vote between
conflicting files. The output list makes the result reviewable. The boundaries
protect tone and privacy. The final search turns “check your work” into something
we can see.

## Do not let the completion message do the inspecting

Suppose the first result looks like this. This output is constructed so that we
can practise catching a realistic failure.

```text
Completed. All public dates and times now match the approved organiser's note.

CLASS OF 2002: ONE MORE NIGHT UNDER THE DISCO BALL

Saturday 17 October 2026
7:00–11:00 p.m. · Starlight Roller Rink

Dig out the butterfly clips. Leave the dial-up modem at home.
RSVP by 15 September using the public RSVP link.

Footer: See you Saturday 10 October.

Website changes
- Change <title> from October 10 to October 17.
- Change the start time from 6:30 p.m. to 7:00 p.m.
```

The opening sentence says every date is fixed. The invitation itself disagrees.
The old date is still in the footer.

That is not a mysterious AI problem. It is a dependency problem. One changed
fact appeared in several places, and one occurrence survived. The model's
summary is a claim about the work; it is not evidence that the work happened.

## Give a targeted correction

Do not restart the whole job or write “wrong, try again.” Point to the proven
defect, restate the controlling fact and ask for the affected dependencies to be
checked while everything else stays put.

```text
The completion statement is not supported by the invitation. Its footer still
says “Saturday 10 October”.

Correct that footer to match the approved organiser's note: Saturday 17 October
2026. Then search the complete proposed invitation and website change list for
every form of the old date and old start time, including “October 10”,
“10 October” and “6:30”.

Preserve all unaffected approved wording. Return:
1. the complete corrected invitation;
2. the exact website changes; and
3. a final occurrence table with the location, old value, final value and check
   result.

Do not call it complete if an occurrence has not been inspected.
```

The corrected result should now be complete enough to inspect directly:

```text
CLASS OF 2002: ONE MORE NIGHT UNDER THE DISCO BALL

Saturday 17 October 2026
7:00–11:00 p.m. · Starlight Roller Rink

Dig out the butterfly clips. Leave the dial-up modem at home.
RSVP by 15 September using the public RSVP link.

Footer: See you Saturday 17 October 2026.

WEBSITE CHANGES
1. <title>: “Class of 2002 Reunion — October 10”
   → “Class of 2002 Reunion — October 17”
2. Event line: “Saturday October 17, 2026 · 6:30–11:00 p.m.”
   → “Saturday October 17, 2026 · 7:00–11:00 p.m.”
3. RSVP link: no change.

FINAL OCCURRENCE CHECK
Invitation heading date | October 10 → October 17 | corrected
Invitation time          | 6:30 → 7:00             | corrected
Invitation footer date   | October 10 → October 17, 2026 | corrected
Website page title       | October 10 → October 17 | change specified
Website event date       | October 17               | already correct
Website start time       | 6:30 → 7:00             | change specified
RSVP deadline            | September 15             | already correct
```

In Chat, this is an approved copy package and change list; you still make the
file changes. In Work, ask for the actual invitation file, then open that file
and inspect the heading, body and footer. In Codex, ask it to edit the exact
website folder, identify every changed file, run a search for the retired values
and open or test the resulting page. A report that says “updated” is not the
same as seeing the updated artifact.

## A Work brief for the invitation file

If Work is available and you want a finished document, add this to the source
pack:

```text
Create the corrected invitation as an editable document and a PDF. Use the
approved copy exactly. Keep the early-2000s feeling in the visual styling, but
do not add event facts or generated contact details.

Before finishing, inspect the rendered PDF at normal reading size. Confirm that
the date, time, venue, RSVP deadline and footer are visible and agree. Report
the filenames and any item you could not verify.
```

Open the document and PDF. Check the footer yourself. A beautiful invitation
with the wrong Saturday is still the wrong invitation.

## A Codex brief for the website

If Codex is available and the website folder is in scope, use a bounded brief:

```text
In the reunion website folder, update only the public event date and time to the
approved values in organiser-note.txt.

Required changes:
- every public October 10 reference becomes October 17;
- the public start time becomes 7:00 p.m.;
- the end time remains 11:00 p.m.;
- the RSVP deadline and link remain unchanged;
- do not open, copy or modify private-rsvp.csv.

Search the website files for all old-date and old-time variants before editing.
After editing, repeat the search, run the site's existing checks, and preview the
page if a preview is available. Tell me the exact files changed, the checks that
passed, and anything you could not visually verify. Do not publish or deploy.
```

The folder limit and “do not publish” line define its authority. The excluded
file names the privacy boundary. The before-and-after search catches hidden
occurrences such as page titles and metadata. The preview checks the thing a
guest would actually see.

## What applies on Free and paid plans

OpenAI currently lists Work and Codex across Free, Go, Plus, Pro, Business, Edu
and Enterprise, with usage shared across Work and Codex. That does **not** mean
every plan has identical limits, models, controls or capacity.

### Applies to both

- Set a clear goal and source of truth.
- Include current job facts in the current prompt or project.
- Exclude private material the job does not need.
- Use the model and controls actually visible in the account.
- Inspect the real text, file or website.
- Correct the smallest proven defect and recheck its dependencies.

### Free route and limit

You can complete the core lesson in an ordinary Chat: paste the three fictional
sources, ask for the discrepancy table and corrected copy, then inspect the
result. If Work or Codex is visible, you may use it within the limits shown in
your account. If a model picker, Max, Ultra, file tool or local execution option
is absent, there is nothing for you to unlock inside the prompt. Use the
available route and do the file step manually.

### Paid difference or extension

A paid plan may provide more capacity, model choice, tools or execution options.
That can make a larger folder, finished file or longer-running website job more
convenient. It does not make weak source material true, grant permission to use
private data or remove the need to inspect the output.

### No equivalent

There is no paid-plan equivalent of deciding which note is authoritative.
There is no setting that can recover a fact you never supplied. There is no
effort level that can approve the invitation on your behalf.

## Can you explain the four choices now?

Try this without looking back:

> A model is ________. Effort changes ________. Chat, Work and Codex change
> ________. A plan changes ________. None of them replaces ________.

A sound answer is: the model is the engine doing the work; effort changes how
much reasoning time it receives; the surface changes where and how it can act;
the plan changes access and capacity; none replaces reliable sources and
inspection.

Your wording does not need to match mine. The distinctions do.

## Try it somewhere new

A neighbourhood association changed its meeting from Tuesday to Thursday. An
old PDF, a webpage and a volunteer's email draft all contain versions of the
details. The membership spreadsheet is private.

Before using ChatGPT, write down:

1. Which source is allowed to overrule the others?
2. Do you need corrected words, a finished PDF or changes to the actual website?
3. Which model and effort would you start with, if those controls are available?
4. Which file will you exclude?
5. Which old values and dependent statements will you search for at the end?

If you can answer those five questions, you are no longer hoping ChatGPT will
“sort it out.” You are directing a job that can be checked.

## The habit to keep

Your first useful ChatGPT skill is not writing longer prompts. It is separating
the choices that matter:

- where the work needs to happen;
- which model fits the shape of the task;
- how much effort the task has earned;
- what your account actually allows;
- which source controls the facts; and
- what evidence will prove the result.

Begin with the account you have. Give it a job you can describe and a result you
can inspect. That is more useful than chasing a perfect prompt — and much less
likely to send the entire Class of 2002 to an empty roller rink.
